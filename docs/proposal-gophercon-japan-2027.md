## 2. Description (セッション概要)

> 文字数：378 文字（制限：日本語 400 字以内）

```text
Kubernetes 1.35でGAとなったIn-Place Pod Resizeにより、Pod再起動なしでメモリ枠を変更可能になりました。しかしGoアプリは起動時にGOMEMLIMITを固定するため、枠が広がっても自動追従できずGC過剰でCPUを浪費します。

本セッションでは、cgroup v2環境下でメモリ増減時にGoランタイム内部で何が起きるのかを実機検証を交えて解き明かします。さらにGo 1.25で先行導入されたCPU自動追従機構（GOMAXPROCS）の内部スキャン構造や、Go公式で議論中のメモリ自動認識プロポーザル（Issue #75164）、そして「Goのヒープ」と「カーネルが見るRSS」の乖離という設計課題まで深掘りします。

コンテナでGoを運用するエンジニアが、次世代のインフラ協調型ランタイムの姿を掴める知見をお届けします。
```

## 3. アウトライン（発表の構成・時間配分）

※ 採択審査の参考として使用（非公開）

- **合計時間**: 30 分想定

### 1. 導入と背景（5 分）
- Kubernetes In-Place Pod Vertical Scaling (KEP-1287: v1.35 GA) のインパクト
- Go におけるメモリ管理の変遷（GC 機構と Go 1.19 `GOMEMLIMIT`）
- 問い：「コンテナが稼働中にリサイズされたとき、Go ランタイムはどう振る舞うのか？」

### 2. 実機検証：動的リサイズで何が起きたか？（7 分）
- cgroup v2 環境（Linux 6.11 / k8s v1.36+）での実験
- メモリ削減時の仕様挙動（`Forbidden: memory limits cannot be decreased unless resizePolicy is RestartContainer`）と安全設計の背景
- メモリ増加時の挙動：再起動ゼロ（`RESTARTS: 0`）での成功と、起動時の `460MiB` に固定されて追従できない Go ランタイムの観測

### 3. なぜ追従できないのか？（Go ランタイムの内部構造）（6 分）
- `src/runtime/mgc.go` における `readGOMEMLIMIT()` の 1 度限りの初期化
- `runtime/debug.SetMemoryLimit()` による動的変更インターフェース
- 発生する実害：物理メモリが余っているのに、古い上限で GC が頻発して CPU を浪費するメカニズム

### 4. 現場での解決策：動的追従の PoC（4 分）
- cgroup v2（`/sys/fs/cgroup/memory.max`）を監視して `debug.SetMemoryLimit` を呼ぶ最小実装
- デファクトな既存ライブラリ（`automemlimit`）のブランクインポートにおける制約（起動時 1 回のみ）と動的追従の実装ポイント

### 5. 次世代の展望：言語本体の動向と設計の深層（6 分）
- 先行事例：Go 1.25 で導入された `GOMAXPROCS` の cgroup 自動認識と内部の「低頻度スキャン機構」
- メモリ側の最新プロポーザル（[golang/go#75164](https://github.com/golang/go/issues/75164)）の動向
- 議論の核心：コア開発者（Michael Knyszek 氏）が悩むマジックナンバー問題（「なぜ 90% なのか」）
- コラム的深掘り：「Go のヒープ」と「カーネルが見る RSS（物理メモリ実占有量）」のギャップと、安全なメモリ返還の未来

### 6. まとめ（2 分）
- クラウドネイティブインフラと協調する Go ランタイムの未来像
