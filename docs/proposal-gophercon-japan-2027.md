# 案 1：チャレンジセッション（20 分）

### 1. プロポーザルタイプ
- **チャレンジセッション**

### 2. Description (セッション概要)
> 文字数：348 文字（制限：400 字以内）

```text
Kubernetes 1.35でGAとなったIn-Place Pod Resizeにより、Podを再起動せずにメモリ枠を動的変更できるようになりました。しかしGoランタイムは起動時にGOMEMLIMITを固定するため、枠が広がっても自動追従できず、GCが過剰発生してCPUを浪費します。

本セッションでは、cgroup v2環境での実機検証ログをもとに、メモリ枠変更時に内部で何が起きていたのか、なぜ追従できないのかをランタイムのコード（mgc.go）から確認します。あわせて、アプリケーション側から動的に追従させるアプローチを実証し、今後の展望としてGo公式の議論状況（Issue #75164等）にも触れます。

KubernetesとGoランタイムのメモリ管理に関心がある方に向けて、検証から得られた気づきと仕組みを共有します。
```

### 3. チャレンジセッションの挑戦内容（任意入力）
```text
初めての大規模カンファレンス登壇への挑戦。単なるライブラリ紹介にとどまらず、手元クラスタでの実機検証ログとGoランタイム内部コード（mgc.go）の読み解きをもとに、現場のエンジニアが持ち帰れる学びを20分で分かりやすく伝え切ることに挑みます。
```

### 4. アウトライン（発表の構成・時間配分）
※ 審査用（非公開）

- **0〜3分 (導入)**: Kubernetes In-Place Pod Resize (v1.35 GA) と `GOMEMLIMIT` の基礎
- **3〜8分 (実機検証)**: 再起動なしでのメモリ拡張成功と、古い上限（460MiB）に固定されて追従しない Go ランタイムの観測
- **8〜12分 (内部構造)**: `src/runtime/mgc.go` における初期化コードと `runtime/debug.SetMemoryLimit`
- **12〜15分 (現場での対処)**: cgroup v2 監視による動的追従アプローチと PoC 実装
- **15〜19分 (今後の展望)**: Go 1.25 CPU 先行例、Issue #75164、なぜ 90% 固定が危険か（ヒープと RSS の乖離）
- **19〜20分 (まとめ)**: クラウドネイティブインフラと協調する Go ランタイムの未来像

# 案 2：ショートトーク（5〜7 分）

### 1. プロポーザルタイプ
- **ショートトーク**

### 2. Description (セッション概要)
> 文字数：301 文字（制限：400 字以内）

```text
Kubernetes 1.35でGAとなったIn-Place Pod Resizeにより、Podを再起動せずにメモリ枠を動的変更できるようになりました。しかし、稼働中に枠を広げてもGoランタイムは起動時のGOMEMLIMITを保持し続けるため、自動では追従できずCPUを浪費します。

本ショートトークでは、手元のクラスタで動的リサイズを実行した際の実機ログをもとに、「なぜGoは追従できないのか」「コンテナを再起動せずに追従させるにはどうすればよいのか」をコンパクトに共有します。

KubernetesとGoランタイムのメモリ管理に関心がある方に向けて、短時間で持ち帰れる実践的な気づきをお届けします。
```

### 3. アウトライン（発表の構成・時間配分）
※ 審査用（非公開）

- **0〜1分 (問い)**: 「Kubernetes でメモリ枠を動的に増やしたのに、中の Go アプリが重い？」
- **1〜3分 (実機ログ)**: cgroup は広がったが、`GOMEMLIMIT` は古い値のまま凍結される事実
- **3〜4分 (原因)**: 起動時に 1 回しか読まない Go ランタイム（`mgc.go`）
- **4〜6分 (解決策)**: `debug.SetMemoryLimit` を使った動的追従アプローチ
- **6〜7分 (まとめ)**: 今後の標準化（Issue #75164）への期待とまとめ
