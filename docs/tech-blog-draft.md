## 第 1 章：前提：コンテナのメモリが「再起動なし」で変わる時代

Kubernetes 1.27+ で策定された In-Place Pod Vertical Scaling (KEP-1287) により、Pod を再起動せずにコンテナの CPU やメモリ制限を変更できるようになりました。

- **従来の常識**: リソース変更＝Pod の再作成（再起動）。接続切断やインメモリキャッシュの破棄が発生していた。
- **In-Place Resize の仕組み**: プロセスを殺さず、kubelet が Linux カーネルの cgroup 設定（`/sys/fs/cgroup/memory.max` など）を直接書き換える。
- **今回の検証の問い**: 「インフラ側でメモリ枠が動的に広がったとき、中の Go ランタイム（GC やメモリ管理）は本当にその変化に追従できるのか？」
